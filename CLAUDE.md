# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

npm workspaces monorepo (`apps/server`, `apps/web`), Node 24.

- `npm run dev` — API (NestJS, :3000, `nest start --watch`) and web (Vite, :5173, proxies `/api`) together
- `npm test` — Vitest in both workspaces (server specs plus the web chart helpers); single file: `npx vitest run src/importers/parsers/workday.parser.spec.ts` from `apps/server`, or filter by name with `-t "pattern"`
- `npm run lint` / `npm run format:check` / `npm run typecheck` / `npm run build` — all run in CI
- `npm run db:generate -w apps/server` — generate a Drizzle migration after editing `apps/server/src/database/schema.ts` (migrations apply automatically on startup)
- `npm run seed -w apps/server [username] [--remove]` — add (or delete) demo jobs tagged `demo` for local development (`src/seed.ts`, runs with tsx against `DATA_DIR`)
- `docker build -t jobify .` — production image (single container: API serves `apps/web/dist`)

## Architecture

- **Server is ESM NestJS 12.** Relative imports need `.js` extensions. Constructor-injected services must be value imports (not `import type`) because Nest resolves them via `emitDecoratorMetadata`; ESLint's `consistent-type-imports` is disabled for the server for this reason. Specs construct services directly rather than through Nest's testing module (Vitest doesn't emit decorator metadata).
- **Database:** SQLite through `@libsql/client` + Drizzle (`database/database.ts`). `better-sqlite3` is deliberately avoided because npm 11 blocks its native build script. Tests use `createTestDatabase()` from `database/testing.ts` (in-memory, real migrations, plus a `createUser` helper). drizzle-kit omits `ON DELETE` on columns added via `ALTER TABLE`; check generated migrations and add it by hand.
- **Config** is a plain typed object from `config/configuration.ts`, injected with the `APP_CONFIG` token. No `@nestjs/config`.
- **Validation:** global `ValidationPipe` with `whitelist` + `forbidNonWhitelisted`, so every accepted body field needs a class-validator decorator on its DTO.
- **Users and auth:** multi-user with private data. `AuthGuard` (global `APP_GUARD`) resolves the session cookie to a user on every route; opt out with `@Public()`, restrict with `@AdminOnly()`, read the user with `@CurrentUser()`. Sessions are random tokens stored as SHA-256 hashes in `sessions`; passwords use scrypt (`users/passwords.ts`). **Every job query must filter by `userId`**, so services take the owner's id as their first argument (see `JobsService`), and events are scoped through their job. `jobs.user_id` is nullable only for pre-accounts data, which `UsersService.createFirstAdmin` claims during first-run setup (confirmed with the legacy `JOBIFY_PASSWORD` when set). The AI provider lives in the instance-wide `settings` table (admin-only); profiles live on `users.profile`. `src/cli.ts` has `list-users` / `reset-password` for recovery.
- **Importers** (`importers/`): an ordered `JOB_PARSERS` list. `ImportService` runs every parser whose `matches(url)` is true, merging results with `fillMissing` (earlier parsers win), and stops once title, company and description are present. Site parsers (with `site` set; API-based) come first, then the generic ones: `JsonLdParser`, `RenderedPageParser` (selector profiles for pasted Indeed/Glassdoor/Workday/... markup), `EmbeddedJsonParser` (job objects in `__NEXT_DATA__`-style script JSON) and `WebPageParser` (title/OpenGraph + best description block via `page-signals.ts`). `PageContext` fetches the page lazily, so API-based parsers never download HTML. Import returns a draft only; the client saves it. Pasted HTML gets its URL from `<link rel=canonical>`/`og:url` so site parsers still run; pasted text goes through `text-draft.ts`. If no site parser matches, `findEmbeddedPosting` looks for an ATS posting embedded in the page (iframe, `?ashby_jid=`, `?gh_jid=`) and parses that instead. Parsers marked `fallback` (`WebPageParser`) are overridden by AI extraction when the user enables AI. After parsing, `enrichDraft` fills missing salary/location/workplace/employment from the text using the heuristics in `text-signals.ts`, and pages that link to many postings are rejected as listings. Use `spacedText()` rather than cheerio's `text()` when matching words: `text()` runs adjacent elements together.
- **AI** (`ai/`): `createAiProvider(settings)` picks a provider. Anthropic uses the official `@anthropic-ai/sdk`; the others use plain `fetch` via `postJson`. Providers throw `AiProviderError`, which `AiService` maps to a 400 (misconfigured) or 502 (upstream failure). Each `AiTask` writes its output to a job column (`AI_TASK_FIELDS`). AI settings saved in the DB override the `AI_*` env vars; the API key is never returned to the browser.
- **Logging:** `main.ts` installs `FileLogger` (console + `DATA_DIR/logs/jobify.log`, rotated by `RotatingFile`), a global `LoggingExceptionFilter` that logs failed requests (4xx as warnings, 5xx as errors), and `requestLogger` for every request at debug level. Use Nest's `Logger`, not `console`. The web app reports uncaught errors and route crashes to `POST /api/logs/client` (`web/src/lib/reportError.ts`).
- **Status history:** `JobsService.update` writes a `status_change` event when the status changes and sets `appliedOn` on the first move out of `saved`. The dashboard's response rate depends on these events.
- **Timeline charts:** `GET /api/jobs/timeline?includeArchived=` returns jobs with their status history; `web/src/lib/gantt.ts` (`buildGanttRows` → `renderGanttSvg`) and `web/src/lib/sankey.ts` (`buildSankey` → `renderSankeySvg`, hand-rolled layout with statuses as fixed columns) each render a self-contained SVG string that the Timeline page shows and exports (PNG via canvas). These pure functions have Vitest specs in `apps/web` (`npm test -w apps/web`). Routes opt into full width with `handle: { fullWidth: true }`, which `Layout` reads via `useMatches()`.
- **User preferences:** per-user UI settings (currently the dashboard card order and hidden cards) live in `users.preferences` (JSON) rather than browser storage so they follow the user between devices. `users/preferences.ts` defines `DASHBOARD_CARDS` and `normalizeDashboard`, which drops unknown cards and appends new ones; `GET`/`PUT /account/preferences`. The web mirrors the card list in `api/types.ts`, and `DashboardPage` renders cards from a `CARDS` registry inside a dnd-kit sortable grid with an optimistic `useUpdatePreferences`.
- **Web:** all server state goes through TanStack Query hooks in `web/src/api/hooks.ts`. `web/src/api/types.ts` mirrors the server's constants and response shapes by hand, so update it whenever DTOs or the schema change. Job list filters live in the URL (`lib/useJobFilters.ts`). Use `cn()` (clsx + tailwind-merge) for class names.
